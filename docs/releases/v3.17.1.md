## 版本说明

一条工具缺陷修复加一条判据路由补充：`list_network_requests` 的 URL 预览不再静默截断（配套 `camoufox-reverse-mcp v1.13.1`），链路 B 明确区分「业务码拒绝 / 响应体 0 字节 / 带明确文案的业务码」三种形态的入场顺序，并沉淀同平台多入口判据差异的案例。

## 主要变更

- **链路 B 增加响应形态三分表（`references/problem-routing.md`、`SKILL.md`）**：
  - 业务码非 0 的 JSON：服务端明确拒绝，从动态值与请求形态入手；
  - **HTTP 200 + 响应体 0 字节（或仅空壳字段）**：多半是渠道、终端或会话身份判定，签名常不是主因，第一步应是**换入口或换端取同一份数据比判据**；
  - 业务码 + 明确文案（未登录、无权限、地区不支持）：服务端已指出缺什么，按文案补条件，不投入签名分析。
  - 明确写出这条判断依据：零字节响应与「签名算错」的对外现象常不可区分，先入为主归因签名会把最贵的路排在第一。
- **`list_network_requests` 预览契约（`references/mcp-tool-reference.md` 同步说明）**：MCP v1.13.1 起 URL 超过 200 字符以 `…` 结尾并置 `url_truncated` / `url_length`；读查询参数、签名或 token 前先用 `get_network_request(request_id=...)` 取完整值。
- **新增案例 `cases/multi-entry-h5-detail-login-gate-vs-sign-gate.md`**：同一商品在同一平台的两条 H5 详情入口上判据完全不同——一条要求动态签名加会话环境、另一条只要求登录态并直接返回「未登录」文案；记录从「误判为签名缺失」到「换入口一步定层」的纠偏过程。

## 兼容性

- 入口行数预算（`SKILL.md < 220` 行）、模板目录与既有工作流不变；预览字段说明需配套 `camoufox-reverse-mcp >= 1.13.1`，旧版仍可用但 `url_truncated` / `url_length` 不存在。
