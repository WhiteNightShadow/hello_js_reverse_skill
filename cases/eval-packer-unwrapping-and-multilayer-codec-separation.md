# 动态 eval 打包壳脱壳、三层独立编解码隔离与会话单次配额边界

> 难度：★★★★
> 还原方案：R3 + R1 混合（离线沙箱接管动态脱壳定位三组件分工 + `jsdom` 标定会话流式密钥流 + 独立还原参数摘要与响应解压链）
> 实现语言：Node.js / Python
> 最后验证日期：2026-11-20
> 平台类型：通用（已脱敏）
> 适用范围：授权测试目标上的业务流查询接口；仅验证单目标当前前端构建版本短批次
> 到达层级：S3（请求签名、请求体信封与响应体解码往返一致并取回真实业务条目）；未到 S4（受服务端单次会话令牌配额约束）
> 失效条件：外层打包器改版、参数摘要盐值或拼接顺序变更、会话令牌签发接口调整或响应侧静态掩码表换版

本案例已移除全部站点域名、静态资源域名、厂商与保护器标识、脚本文件名、全局变量名、硬编码盐值、接口路径与请求头名，并彻底排除任何交互式验证绕过内容，仅保留动态 `eval` 打包壳前置脱壳、三层独立密钥/编解码域隔离、Latin-1 二次 UTF-8 编码膨胀判读以及单次会话配额边界的通用定位方法。结论仅对当时的受控测试样本成立，不是全局规则。

## 背景

目标页面在发起核心业务查询前动态加载三个数千行级混淆脚本，分别承担「XHR/fetch 统一请求拦截与信封封装」「会话令牌交互与响应体解码」「辅助环境采集」三项职责。接口同时存在三层保护与配额约束：
1. **外层 `eval(function(...) {...})` 自解码壳**：三个大体积脚本表面看似虚拟机字节码，实则在初始化阶段通过 `eval` / `Function` 动态还原出数百 KB 的可读 JS 源码再执行。
2. **三套互不相干的哈希/流密码体系**：查询参数带 32 位十六进制摘要；POST 请求体被封装成「明文摘要前缀 + 流密码密文（经 Latin-1 → UTF-8 → Base64 编码）」；HTTP 200 响应体则是另一套静态掩码表异或后再经 `zlib` 压缩的密文。
3. **严格的会话凭据单次放行配额与试错降级**：预检接口签发的会话凭据在真实页面内同样遵循单次消费语义，且短时间高频发送错包会将当前出口直接推入持续 `403` 状态。

## 走过的链路

1. **先区分「动态代码脱壳包」与「真字节码 JSVMP」**。拿到 `eval(function(...){...})` 形态的大脚本时，不急于按字节码虚拟机下探 opcode，而是在断网的本地受控沙箱中包装全局 `eval` 与 `Function` 构造器，将每次传入的顶层自包含源码文本按序号写入工作目录并记录原始包与脱壳产物的 `sha256`（按 ECMAScript 规范，在 JS 层包装 `eval` 会使其退化为间接 `eval`、无法读取外层函数局部词法变量；若内层依赖闭包局部变量的直接 `eval`，应保持原生 `eval` 不变而仅对入参做源码包裹 `eval(__tap(expr))` 或用原生断点读取；若动态代码嵌在异步 JSON 响应字段内，可先用 `save_response_body` / `get_network_request` 取回响应再按 JSON 路径提取落盘，见 [混淆识别与还原指南](../references/obfuscation-guide.md)）。脱壳后三份脚本直接还原为结构清晰的模块代码，省去字节码逆向成本。
2. **先切分三层独立密钥域，再逐层做往返验证**。对照脱壳后的发送拦截器与响应处理函数，确认三处变换互不共享密钥：
   - **层一（查询参数摘要）**：对请求参数按键名排序并规范化数组/对象序列化后拼接固定盐做哈希，用 3 组抓包样本离线逐字对齐；
   - **层二（请求体流式信封）**：明文 JSON 先算摘要前缀，再与派生的等长密钥流 `KS` 逐字节异或；通过受控改变会话凭据与 `navigator.userAgent` 证实 `KS = F(会话凭据, UA 内核族)`——更换会话凭据或将 Firefox UA 换成 Chromium UA 都会导致整张密钥流完全改变；同时核对编码出口发现密文字节经 `latin1 → utf8 → base64` 二次编码，按逆序拆解后与抓包请求体逐字一致（详见 [不透明令牌分析](../references/opaque-token-analysis.md)）；
   - **层三（响应体解码与解压）**：响应密文不依赖会话凭据，先经 Base64 与单字节掩码还原、与内置静态位置表异或，最后做 `zlib` 解压得到业务 JSON。但同一解码函数在 Chromium UA 分支下会静默返回序列化的字节对象而非明文字符串，保持与基线一致的 Firefox UA 后直接产出正常 JSON。
3. **核对同名异源设备标识与 `jsdom` 运行边界**。装包比对时发现请求头中的设备标识与 Cookie 中的近似缩写字段并非同一值，明文信封内必须填入请求头那一侧的标识才能通过校验（见 [签名来源隔离](../references/signature-source-isolation.md)）。同时验证发现核心令牌函数在裸 `node:vm` 中因全局原型差异触发异常分支导致哈希轮数暴涨，迁入 `jsdom` Realm 并启用受控子资源加载后在毫秒级正常返回且拦截器稳定挂载（见 [原始 SDK 运行](../references/original-sdk-runtime.md)）。
4. **用页面同条件对照确认 S4 配额边界并守住试错红线**。首条请求在 S3 成功返回完整业务列表后，复用同一会话凭据发第二条立即收到 `403`；回到干净浏览器观察页面自身切换栏目的第二次请求，确认同样触发 `403` 并在重新签发凭据后才放行，从而排除“本地信封第二次才算错”的误判。排查初期曾因高频发送测试包导致当前出口从常规业务拦截降级为无差别 `403`，后续严格通过实验台账门禁限制每批请求数（见 [对照实验](../references/controlled-experiments.md)）。

## 假设与纠偏

| 当时的假设 | 推翻它的证据 | 现在的结论 |
|---|---|---|
| 三个大体积混淆文件都是字节码 JSVMP，需要插桩解释器 | 离线沙箱拦截 `eval` / `Function` 入参后直接落盘出数十万字节可读 JS 源码 | 遇到外层自解码壳先做离线动态入口脱壳，确认脱壳产物仍是字节码解释器时再上 VMP 四板斧 |
| 请求加密与响应解密共用同一套流式密钥流 | 拿标定无误的请求侧 `KS` 在偏移 `0..63` 扫描响应体全部为乱码；阅读脱壳源码确认响应侧为静态表加 `zlib` | 同一接口的参数签名、请求信封与响应编码可能是独立演进的三套组件，先定边界再分别往返验证 |
| 流式密钥流是写死在脚本里的全局常量表 | 保持其余输入不变，仅替换会话凭据或切换 Firefox / Chromium UA 后 `KS` 逐字节全变 | 流式掩码常由会话凭据与环境内核分支共同派生，标定必须在成套会话与固定基线 UA 下进行 |
| 请求头与 Cookie 里名字相近的设备字段可以互换 | 混填 Cookie 侧缩写字段后服务端立即报校验失败，改回请求头侧对应标识即通过 | 名字相近的客户端标识先在抓包样本中核对值是否相等，不凭字段名猜测同源 |
| 第二次请求 `403` 说明本地信封存在状态泄漏 | 在未挂任何 Hook 的干净浏览器内触发同凭据第二次请求同样返回 `403` | 判断 S4 失败原因前先在干净页面验证真实配额语义，区分「单次放行策略」与「本地实现缺陷」 |

## 可以带走的和带不走的

可以带走的是四条通用判断：
1. **先验壳再定分析深度**：遇到 `eval` / `Function` 包装的大脚本先在离线沙箱脱壳看内层形态，避免在打包壳上空耗字节码逆向精力。
2. **多层保护先画密钥域边界**：把查询签名、请求体信封、响应体解码拆成独立往返实验，同时留意 `latin1 → utf8 → base64` 造成的约 `1.5×` 长度膨胀特征。
3. **固定基线 UA 族与核对相近标识**：UA 分支不仅影响请求特征，还可能切换 SDK 内部的密钥派生表与响应解码返回类型；请求头与 Cookie 中的相似标识须逐字核实来源。
4. **把出口与会话状态当作不可再生预算管理**：连续无效试错会把正常业务响应恶化为无差别 `403`，严格遵守单批小预算与遇拒即停纪律。

带不走的是单目标的具体盐值、参数拼接细节、特定请求头组合、静态异或表字节以及单次放行配额的具体数值。

## 可验证事实清单

- [ ] 遇到 `eval` / `Function` 外层包装脚本时，是否已在离线沙箱脱壳并记录原包与脱壳产物的 `bytes + sha256`
- [ ] 请求签名、请求体信封与响应体解码是否已分别建立独立的离线往返断言，未混用不同层的密钥流
- [ ] 本地运行时的 UA 内核族是否与抓包基线严格一致（未混入跨内核独有全局对象）
- [ ] 请求头与 Cookie 中的设备/会话标识是否已逐字段核对值来源，并通过干净页面对照确认了凭据复用配额
