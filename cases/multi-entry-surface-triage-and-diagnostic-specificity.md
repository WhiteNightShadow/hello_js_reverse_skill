# 同实体多入口闸门与诊断显式度分离、控制组失效判读及超长 URL 预览截断纠偏

> 难度：★★★☆☆
> 还原方案：D: 浏览器与协议对照取证（基线分流与前置依赖定层，未进入签名还原）
> 实现语言：Python (`urllib`) + Camoufox MCP 取证
> 最后验证日期：2026-11-25
> 平台类型：通用（已脱敏）
> 适用范围：同一业务实体同时暴露新版 CSR 聚合入口与传统详情入口的多端站点；**未登录**访客会话；MCP v1.13.1
> 到达层级：S2（明确服务端前置鉴权缺口，未提供登录态故未达 S3）
> 失效条件：任一入口下线、网关统一收口为同一鉴权中间件，或引入登录态后返回字段集合变化（需重验 S3 字段完整度）

本案例的结论只对上述范围成立，不是全局规则。

---

## 一句话结论

当主入口在**真实浏览器页面内（控制组）**即返回 `HTTP 200 + 0 字节` 空响应体与模糊风险提示时，不应先入为主将其归因为“缺少或算错动态签名”而直接投入 JSVMP 逆向：一方面需用完整请求详情（而非被 200 字符截断的 URL 预览）核实真实请求是否已携带签名；另一方面，若同一业务实体存在其他官方入口，横向请求一次往往能以极低成本区分“全局前置登录依赖”与“单通道签名/环境策略”。

## 技术指纹

### 1. 同实体双入口与旁路噪音特征

- **入口 A（新版 CSR 分享/详情聚合页）**：
  - 首屏 HTML 仅约 `12 KB` 空壳容器，核心业务数据完全依赖单条聚合接口：
    `POST /api/v2/catalog/item-pack?scene=share_view&fp_id=<指纹标识>&session_tok=<会话令牌>&req_sig=<动态签名>`
  - 请求体为 `application/x-www-form-urlencoded`，携带视图配置 JSON、场景枚举与目标实体 ID。
  - 同页并发两条易混淆的旁路接口：一条仅返回前端开关配置 JSON，另一条仅返回辅助营销摘要，均不含核心实体字段——抓包筛选时需先按响应结构排除非主数据接口。
- **入口 B（传统 Web/H5 详情页）**：
  - 针对同一实体 ID 发起 `GET /api/v1/item/detail?id=<实体ID>&fp_id=<指纹标识>&channel=external`，URL 上不携带 `req_sig` 动态签名参数。
  - 同域伴随库存、计数与支付方式等旁路子接口。

### 2. 参数与票据特征

- **`req_sig`（入口 A 查询串尾部动态签名）**：约 `40–48` 字符 URL 安全编码串，同会话同分钟内每次请求均变化，绑定查询参数顺序、`session_tok`、`fp_id` 与 `User-Agent`；因位于超长 URL 末尾（总长常超过 `230` 字符），在 `200` 字符列表预览中恰好被整段切掉。
- **`session_tok`**：约 `107–128` 字符会话令牌，同时出现在主接口查询串与前置上报接口中。
- **`fp_id`**：与页面可见的非 `HttpOnly` 访客标识 Cookie 同值。
- **`anon_ticket`（跨域匿名会话票据 Cookie）**：`HttpOnly; Secure`，由独立票据中心注册后经 `302`/回调 URL 在目标业务域种下。

### 3. 反调试特征

- 前端未部署 `debugger` 死循环或控制台陷阱；阻断完全发生在服务端响应层（静默空体 vs 显式错误 JSON）。

## 问题定位记录

```text
现象：入口 A 在真实浏览器内返回 HTTP 200 且响应体 0 字节，页面提示当前访问环境异常
失败层：会话层（缺少登录态）叠加入口 A 的渠道/环境策略，而非本地签名算法错误
依据：
  1. 页面控制组自身已携带完整 req_sig + 有效 anon_ticket，仍返回 0 字节（控制组失效）
  2. 同实体切换至入口 B 后，服务端直接返回明示业务码与“请先登录”文案
路线：R6（浏览器取证核对控制组）→ 跨入口判据对比定层；补齐授权登录态后再按需重评入口 B（R0 候选）与入口 A 的 S3 字段覆盖度
结论强度：排除（排除了“浏览器未带签名”与“纯匿名票据缺失即可过入口 A”）+ 支持（当前实体在未登录态下受前置登录门禁约束）
```

## 已验证定位路径

```text
步骤 1：launch_browser + network_capture(action="start", capture_body=True) 打开入口 A
        → 从 60+ 条请求中筛出唯一承载主数据的 POST /api/v2/catalog/item-pack（排除开关配置与辅助文案接口）
步骤 2：检查 list_network_requests 列表摘要与 get_network_request 完整详情
        → 列表预览在 200 字符处截断（MCP v1.13.1 起显式带 "…" 与 url_truncated=True），调用 get_network_request 确认真实请求尾部已带 req_sig，但响应仍为 HTTP 200 + 0 字节（控制组未达 S3）
步骤 3：独立复现跨域匿名票据握手（排除“未建匿名会话”假设）
        → 走 register → callback Set-Cookie → verify 拿到 status=0 通过回执后重测，入口 A 桌面 UA 无签名回通用模糊错误码，移动 UA 及浏览器带签名均回 HTTP 200 + 0 字节
步骤 4：控制组失效分流——横向检查同实体的传统官方入口 B（/web/item/detail?id=<实体ID>）
        → 捕获 GET /api/v1/item/detail 响应：{"code":"AUTH_REQUIRED","msg":"用户未登录，请登录后重试"}
        → 单次请求直接拿到服务端明示缺口，停止在无基线状态下逆向入口 A 的动态签名
```

## 关键经验总结

### 1. `HTTP 200 + 0 字节` 是多因同象，先看页面控制组是否成立

在逆向实战中，静默 `0` 字节或空壳 JSON 本身**不能直接定层**：当浏览器控制组成功、本地重放返回 `0` 字节时，往往指向动态签名、环境指纹或 TLS/伴生头差异；但当**未加改动的浏览器控制组自身也返回 `0` 字节**时，本地精修签名不可能跑赢已经失败的基线。

同一接口在不同请求形态下的响应对比：

| 请求来源与形态 | 实测响应 | 证据含义 |
|---|---|---|
| 本地桌面 UA + 有效匿名票据、无 `req_sig` | `{"code":4001,"msg":"当前网络不稳定"}` | 触发动态值缺失分支，但错误文案本身经过模糊化包装 |
| 本地移动 UA + 有效匿名票据、无 `req_sig` | `HTTP 200`，响应体 `0` 字节 | 静默丢弃体与签名算错/渠道拦截共享同一外部表现 |
| 真实浏览器内、带合法 `req_sig` + 匿名票据校验通过 | `HTTP 200`，响应体 `0` 字节 + 页面风控提示 | **控制组失效**：当前卡点不在“本地签名没算对”，继续抠签名纯属空转 |

### 2. 同实体跨入口对比：同时比较“闸门重量”与“报错显式度”

大型平台常因历史演进保留多条读取同一业务 ID 的官方视图（新版聚合 BFF、旧版详情接口、SSR 首屏注水）。控制组受阻时横向探测同实体其他入口有两个直接收益：
1. **错误回显粒度不同**：新版聚合网关常把未登录、风控与签名错误统一折叠成 `0` 字节或“网络繁忙”；老版接口往往保留直译业务码（如明确返回“未登录”），一步指明缺失的前置条件。
2. **闸门重量可能不同**：部分次级入口仅校验常规登录 Cookie 而不要求动态签名（`R0` 候选）。但若后续准备采用次级入口交付，仍须在补齐登录态后核验 **S3 字段完整度**（优惠后价格、规格库存等字段是否齐全），且绝不能把入口 B“无需签名”的结论反向套回入口 A。

### 3. 分离“跨域匿名会话票据”与“用户登录态”两类 Cookie

部分体系将基础会话拆成两层：第一层是无需账号即可通过 `POST /session/ticket/register` → 跟随带 `ticket` 的回调地址落盘 `HttpOnly` 票据 → `POST /session/ticket/verify` 自建的**匿名设备/域票据**；第二层才是绑定账号身份的**登录态 Cookie**。先用最小脚本把第一层跑通并拿到 `verify` 通过回执，才能严谨排除“连基础 Cookie 罐都没建好”的低级干扰。

## 假设与纠偏

| 当时的假设 | 推翻它的证据 | 纠偏后的结论 |
|---|---|---|
| “列表里的 URL 末尾停在 `session_tok`，说明页面没发签名参数” | 调用 `get_network_request` 读取完整 URL，发现 `200` 字符之后还有 `&req_sig=...` | 列表 `url` 只是定长预览；判断查询参数、签名或令牌是否存在前必须先看 `url_truncated` 并取完整请求详情 |
| “入口 A 返回 `0` 字节是因为缺少或算错了动态签名” | 真实浏览器内已带原生 `req_sig` 与有效匿名票据，响应依旧是 `0` 字节 | 控制组本身未过；在基线恢复到 S3 之前不做任何本地签名归因 |
| “必须先把入口 A 的 JSVMP 签名啃下来才能知道为什么拿不到数据” | 同一实体在入口 B 一条 GET 请求即返回明文“未登录”错误码 | 基线受阻时优先做同实体跨入口对照，用显式报错入口定层前置依赖 |
| “App 内嵌详情页必须拆包或 Root 抓原生通道才能看协议” | 实测该详情视图在端内同样是标准 HTTPS Web 页面 | 先区分原生 RPC 与内嵌 H5，后者直接通过常规浏览/抓包取证即可 |

## 踩坑记录

| # | 坑 | 现象 | 解决方法 |
|---|---|---|---|
| 1 | 直接从 `list_network_requests` 截断预览里数查询参数 | 超长 URL 尾部签名被切掉却像自然结尾，误判成未带签名 | 检查 `url_truncated`（MCP v1.13.1+），一律用 `get_network_request(request_id=...)` 读完整 URL |
| 2 | 把 URL 里的渠道布尔开关（如 `in_app=0`）当成拒绝主因 | 正常外部浏览器成功样本里该字段同样为 `0` | 用真实成功样本或显式报错入口做对照，不凭字段名猜业务逻辑 |
| 3 | 把未登录态下的默认占位参数（如 `device_id=0`）当成构造缺陷 | 页面自身未登录请求同样发送 `0` | 先对齐页面自身控制组，区分“未登录态正常默认值”与“参数缺失” |
| 4 | 看到某旁路子域单接口返回 `502` 就判定整套旧入口已废弃 | 同批次该子域下另一支付查询接口同样回 `502`，而主详情域正常返回业务 JSON | 区分边缘网关局部异常与主数据接口状态，交叉查看同域其他接口后再下结论 |

## 变体说明

| 入口变体 | 鉴权与闸门特征 | 采集与取证启示 |
|---|---|---|
| 新版聚合详情入口 | 匿名票据 + 动态查询串签名 + 会话/环境策略，拒绝时静默回 `0` 字节 | 诊断成本最高；控制组未过时先停手排查登录态与渠道条件 |
| 传统 Web/H5 详情入口 | 无查询串动态签名，拒绝时直接返回明示业务错误码（如未登录） | 适合快速验证账号/会话前置条件；拟作交付通道前需核验登录后的 S3 字段完整度 |
| 端内内嵌 Web 视图 | 与 H5 共享同类页面结构，仅 UA 或容器桥接头不同 | 无需先假设原生二进制协议，先验证是否为常规 Web 容器请求 |
