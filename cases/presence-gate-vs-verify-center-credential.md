# 参数存在性门禁 vs 内容校验：同一服务两条接口的不同强度

> 难度：★★★☆☆
> 还原方案：B（沙箱执行原始 SDK，喂入-截出）+ A（参数依赖消融）
> 实现语言：Node.js
> 最后验证日期：2026-11-26
> 平台类型：通用（已脱敏）
> 适用范围：同一域下两条相关接口（列表接口与子资源接口）；未登录会话；SDK 为 JSVMP 字节码型
> 到达层级：S3（两条接口都在纯 Node 上取到真实数据；S4 已覆盖多目标与断点续采，跨天未验证）
> 失效条件：签名参数长度或字符集变化；子资源接口开始要求新参数；凭证参数改为一次一签；单页上限变化

本案例的结论只对上述范围成立，不是全局规则。为便于复用，下文用占位名描述实体：

| 占位 | 指代 |
|---|---|
| `LIST_EP` / `SUB_EP` | 列表接口 / 子资源（二级）接口 |
| `SIG_PARAM` | 前端 SDK 生成并追加的签名参数（约 190 字符，含 `-` `/` `+` `=`） |
| `CRED_PARAM` | 验证中心签发给设备的凭证参数（形如 `verify_<8>_<8>_<4>_<4>_<4>_<12>`） |
| `SESS_ID` | 会话标识 Cookie（可由注册接口自举） |
| `CRED_COOKIE` | 与 `CRED_PARAM` 同值的那条 Cookie |

---

## 为什么值得单独成案

同一个域下、同一套前端 SDK、同一个签名参数，**在两个接口上的校验强度完全不同**：

- `LIST_EP`：只校验 `SIG_PARAM` **参数是否存在**，值可以是随机串、甚至空值；
- `SUB_EP`：**校验签名真伪**，并且额外要求 `CRED_PARAM` 是验证中心签发的**真实凭证**。

把前者的结论推广到后者，会得到「必须补环境 / 必须上浏览器」的错误判断。本案例的核心是**定层方法**和一次代价很高的误判纠偏。

## 技术指纹（候选线索）

### JS 特征
- [ ] 单个 380KB+ 的 JSVMP 文件，UMD 导出到 `window.<vendor>_acrawler`，带 `init` / `legacy-sign-entry`
- [ ] 另一个 147KB 的文件注册 `window.<vendor>ms = { init, getReferer }`
- [ ] 页面 inline script 调 `window.<glue-init>(config, resources)`，`config` 内含正则路径列表与 `pageId`
- [ ] 拦截器改写 `XMLHttpRequest.prototype.open` 与 `window.fetch`，对匹配路径的 URL 追加签名参数

### 参数特征
- [ ] `SIG_PARAM`：188~196 字符，字符集含 `-` `/` `+` `=`；同一 URL 连续签名长度小幅波动
- [ ] `CRED_PARAM` / 其同名 Cookie：`verify_<8>_<8>_<4>_<4>_<4>_<12>`
- [ ] `MS_TOKEN`：长 base64 串，**实测可任意值**
- [ ] `SESS_ID`：`1%7C<...>%7C<ts>%7C<md5>`，可由注册接口自举

### 请求特征
- [ ] 缺 `SIG_PARAM` → **HTTP 200 + 响应体 0 字节**（不是错误码，也不是空列表）
- [ ] 子资源接口缺 `CRED_PARAM` → 同样 200 + 0 字节
- [ ] 单页上限固定（本例 50）：`count` 超过上限时仍按上限返回，但响应游标按请求值递增 → 会跳页漏采

### 反调试特征
- [ ] 扁平化解释器（`window._$<name>_<id>`），字节码驱动
- [ ] 载荷整体被掩码：同环境连续采样**没有稳定字节岛**，逐字节 diff 无信息量

### 指纹检测规则（Agent 执行）

```
快速检测命令（30秒内完成）：
  - search_code(keyword="legacy-sign-entry") 或 search_code(keyword="glue-init") → 高置信度
  - scripts(action='list') → 同时存在 380KB+ 与 147KB 两个 sec SDK
  - list_network_requests → 请求带 ~190 字符的签名参数
匹配判定：命中 2 项以上 → 按本案例走
```

## 问题定位记录

```
现象：LIST_EP 返回完整 JSON；SUB_EP 返回 200 + 0 字节
失败层：动态值（签名）——但两条接口的判据不同
  依据：同一个 SIG_PARAM 在 LIST_EP 上任意值都过、在 SUB_EP 上必须真值且串里要有 CRED_PARAM
路线：R0（LIST_EP 不生成）+ B/沙箱（SUB_EP 本地签名）
外部依赖：SESS_ID 自举；CRED_PARAM 一次取得后长期复用
结论强度：证明（存在性门禁 / 内容校验 / 凭证真值约束）
```

## 加密方案

- **算法**：JSVMP 内部字节码，不可静态提取；采用**喂入-截出**：把目标 URL 交给 SDK 拦截器，读回它追加了签名参数的 URL
- **入口归属**：签名参数由 **第二个 SDK 文件**（`window.<vendor>ms`）生成，**不是**那个 380KB 的 JSVMP 文件（后者只产 16 字符的旧式签名）。这是第一个容易走错的定位点
- **绑定范围**：`SIG_PARAM` 与**完整 query 串**绑定（顺序敏感）。必须签"最终要发出的那个串"，不能签完再改参数
- **会话解耦**：签名不绑 `SESS_ID`。全新自举的会话 + 同一个 `CRED_PARAM` 即可

## 已验证定位路径

```
步骤 1: list_network_requests → 找到两条相关请求
步骤 2: get_network_request → 取完整 URL（列表预览会截断，必须走详情）
步骤 3: 消融①：LIST_EP 上 真值 / 同长随机值 / 空值 / 删参数 四组
        → 随机值与空值都过、删参数失败 → 「参数存在性门禁」
步骤 4: 消融②：SUB_EP 上同样四组 → 只有真值通过 → 「内容校验」
步骤 5: search_code(keyword="glue-init") → 取 paths/pageId 配置
步骤 6: 沙箱加载第二个 SDK，伪造 FakeXHR，open() 时读回 URL 里的签名参数
步骤 7: 本地值打 SUB_EP → 先 0 字节；补上 CRED_PARAM → 通过
步骤 8: 比对 CRED_PARAM 与 Cookie → 确认它就是那条同名 Cookie 的值
```

## 🚫 禁动清单

### ❌ 禁动对象 1：看到 0 字节就去补环境
- **理由**：本案例两次把"参数缺失 / 会话过期"误判成"环境指纹不符"，两路补环境全部白做
- **正确做法**：先做**参数依赖消融**（该参数该不该发、值该不该真、串是否一致），再谈环境

### ❌ 禁动对象 2：拿过期抓包当控制组
- **理由**：过期会话原样重放本身就是 0 字节；此时"候选也 0 字节"不含任何归因信息
- **正确做法**：控制组必须"此刻成立"；拿不到新值就用 mock/route 拦截生成**未消费**的签名

### ❌ 禁动对象 3：在掩码载荷上做逐字节 diff
- **理由**：实测同环境连续采样解码后没有稳定字节岛，位置对比只产出噪声
- **正确做法**：先把"值是否被接受"这一层做实，再决定是否值得解载荷

## 踩坑记录

| # | 坑 | 现象 | 解决方法 |
|---|---|---|---|
| 1 | 签名参数归属猜错 | 只加载 380KB 那个文件时永远只有 16 字符旧式签名 | 找第二个 SDK（`window.<vendor>ms`），签名靠它的拦截器 |
| 2 | 列表预览截断 URL | 读到半截 query，误判参数有无 | 一律用详情接口取完整 URL |
| 3 | 签名串与发送串不一致 | 200 + 0 字节 | 签"最终串"；SDK 自补的参数要预先放进串里 |
| 4 | `evaluate` 落在隔离世界 | `typeof window.<sdk>` 是 `undefined`，但脚本确实加载了 | 注入 script 到真世界，或读 `window.wrappedJSObject` |
| 5 | `count` 超过单页上限 | 返回上限条数但游标按请求值递增 | 单页固定 ≤ 上限 |
| 6 | 以为签名一次性 | 重放旧值偶尔失败 | 失败来自会话过期；同一值可重复通过 |
| 7 | 用 shell 传 URL | `&` 被命令行解释器拆开 | 参数数组直传，或把 URL 放环境变量 |

## 假设与纠偏

| 当时的假设 | 推翻它的证据 | 现在的结论 |
|---|---|---|
| 本地签名被拒 = 环境指纹不符，只能靠浏览器 | 换**全新自举会话 + 真实 CRED_PARAM**后，同一份本地签名直接 200 | 失败在参数与会话，不在环境 |
| `CRED_PARAM` 可随意造（同格式即可） | 同格式伪造 → 200 / 0 字节 | 它是验证中心签发的**凭证**，服务端认识它 |
| `MS_TOKEN` 是必需参数 | 换成任意值仍 200 | 不校验，可省 |
| "自建浏览器失败、现成浏览器成功" = 启动配置差异 | 补上 `CRED_PARAM` 后自建浏览器签出的值也能过 | 那只是同一个"参数缺失"的第二个表现面 |

## 关键经验总结

### 1. 「参数存在性门禁」是真实存在的中间强度
调用方看起来"没签名就过不去"，但服务端只判断该参数**在不在**。判定极便宜：**同长随机值 / 空值 / 删参数** 三组各一发。若"随机值通过、删参数失败"，就不要继续还原算法。

### 2. 同服务不同接口必须分别定层
两条接口共用 SDK、共用参数，强度却不同。任何"这个站的签名要不要算"的结论都要带接口范围。

### 3. 区分「算法产物」与「凭证」
签名参数是算法产物（可本地复现）；`CRED_PARAM` 是凭证（服务端认识的具体值）。凭证的复用性通常远高于会话 id，但**不可自造**。识别方法：伪造同格式值仍被拒 → 它是凭证。

### 4. mock / route 拦截可以拿到"签了但没发出去"的签名
把目标路径拦在出网之前（mock 响应或 route 短路），页面照常签名、服务端收不到 → 得到**未消费**的签名，可做控制组或参数模板。这是构造有效控制组最省的手法。

### 5. 控制组失效时停止归因
本案例最大的时间损失来自"控制组本身 0 字节，却继续拿它做对比"。规矩：控制组不成立时先修控制组，任何"候选失败"的结论都不写。

### 6. 主世界与隔离世界
浏览器自动化里 `page.evaluate` 跑在隔离世界，页面脚本定义的全局都看不见。要么注入 script 到真世界，要么读 `window.wrappedJSObject`。这条会反复浪费排查时间。

- [ ] 列表接口带任意/空签名参数 → 仍返回数据（存在性门禁）
