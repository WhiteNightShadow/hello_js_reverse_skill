# 阿里云滑块（AliyunCaptcha / FeiLin）：JSVMP 查表加密 + 行为风控轨迹形态

> 难度：★★★★☆
> 还原方案：A（纯算法还原，最终运行不需要浏览器）
> 实现语言：Node.js
> 最后验证日期：2026-11-14
> 平台类型：通用（阿里云滑块验证码，站点侧只做转发）
> 适用范围：`FeiLin 1.5.4` + `dynamicJS/3.29.0/pe.*.js`（动态 JS 每次会话 hash 不同），2026-11 抓取
> 到达层级：**S3 命中（连续 5/5，缺口位置 160~202）**；S4 可持续未验证（跨天/续期未测）
> 失效条件：SDK 大版本变更（查表种子与表需重解）；风控策略调整；渲染缩放关系变化

本案例的结论只对上述范围成立，不是全局规则。

## 一句话结论

**这是两个独立难点叠在一起，而且第二个才是门槛**：

1. `data` 字段的加密层——一段藏在字节码虚拟机里的自修改查表变换。**可以直接解出来**，离线逐字节复现。
2. 滑块轨迹的**形态**——真人不是平滑曲线，而是「慢逼近 → 谷底犹豫 → 末端甩鞭 → 收尾」。

只解决第 1 条会一直失败：**12 次提交全 false**，即使几何误差 0.24px、可信标记全 1、设备遥测 200。
补上第 2 条后 **5/5 连续通过**。

最反直觉的一点：**通过的那两次 `data` 长度只有 1300 多字符，而我之前"精心构造"的 4688 / 16300 字符的轨迹全 false。**

## 技术指纹（候选线索）

### JS 特征
- [x] `o.alicdn.com/captcha-frontend/aliyunCaptcha/AliyunCaptcha.js`：入口，含 `initAliyunCaptcha`
- [x] `g.alicdn.com/captcha-frontend/FeiLin/<ver>/feilin0NN.<sha256>.js`：父 SDK，字符串池 = 自定义 base64 字母表 + 逐字节 XOR（多个单字节键）
- [x] `g.alicdn.com/captcha-frontend/dynamicJS/<ver>/pe.0NN.<hash>.js`：**每次会话 hash 不同**，由 InitCaptcha 响应的 `StaticPath` 指定，是真正干活的动态 JS
- [x] `pe.*.js` 内含**字节码栈机 VM**：解释器 + 两段字节码（一段生成 nonce，一段做加密层）

### 参数特征
- [ ] `captchaVerifyParam`：JSON 信封 `{sceneId, certifyId, deviceToken, data}` → POST 站点 `?method=slideAuth`
- [ ] `data`：base64，**解码后前 3 字节恒为同一个值**（可作为该产品指纹，非加密常量）
- [ ] `deviceToken`：`base64("WEB#deviceId#cipherB64#len#" + MD5(前四段 + 固定盐))`，盐是硬编码字符串
- [ ] `certifyId` / `Image` / `PuzzleImage` / `StaticPath`：来自 InitCaptcha 响应

### 请求特征
- [ ] 进页面自动 `POST https://<prefix>.captcha-open.aliyuncs.com/`（Action=InitCaptcha，阿里云 RPC + HMAC-SHA1 签名）
- [ ] 拖完才发站点侧 `slideAuth`，**判决只有两个布尔**、无错误码 → **无法用响应小步逼近**
- [ ] 设备遥测 `cloudauth-device-dualstack.*.aliyuncs.com` 必须返回 `ResultObject:true`，否则轨迹再对也白搭

### 反调试特征
- [ ] `FeiLin` 启动时做 WebGL 指纹采集，会打印 `WebGL context was lost`——**这是正常的，不是失败原因**（我在这里浪费过时间）
- [ ] 目标页常把验证码容器设成空 `position:absolute` div、触发按钮设 `visibility:hidden`
- [ ] 加密层不在任何 `crypto-js` / 标准 AES 调用里，静态搜密文特征搜不到

### 混淆类型
- [ ] 字符串池（自定义 base64 + XOR）+ 控制流平坦化（CFF switch）+ **字节码 VM**

### 指纹检测规则（Agent 执行）

```
快速检测（30 秒内）：
  - scripts(action='list') → 同时出现 feilin0NN 与 dynamicJS/pe.0NN 两个 CDN 脚本
  - search_code("captchaVerifyParam") → 命中页面内联脚本
  - 取 data 解码后看前 3 字节是否恒定为同一组值
匹配判定：以上 3 项全中 → 本案例的加密层结论可复用（但种子与表需按当前 bundle 重解）
```

## 逆向思路与过程

### 一、先把链路摸清（不要急着解算法）

用 Camoufox + 网络捕获走一遍完整流程，得到这条链：

```
Log1(设备指纹) → InitCaptcha(拿 certifyId + 两张图 + StaticPath)
  → 加载 FeiLin SDK + 动态 JS → 渲染滑块
  → 拖动 → SDK 内部生成 data → 组装 captchaVerifyParam
  → POST 站点 ?method=slideAuth → 两个布尔
```

**关键认知**：判决只有两个布尔、没有错误码。这意味着**不能靠响应小步逼近**，只能靠控制组对照。
后面所有进展都建立在这一点上。

### 二、加密层：从 btoa 出口倒着挖

一开始我也以为是 AES（3 字节魔数 + 密文，很像）。**静态搜魔数、搜 `crypto-js` 一无所获**——这一步卡了很久。

转折点是放弃静态特征，改从**运行时出口**倒推：

```
步骤 1：Hook window.btoa，记录每次调用的入参长度
        → 发现一串以 "eJ" 开头、长度随轨迹增长的结果（那就是 deflate 的 base64）
步骤 2：对该调用栈下断点，往上一层一层看
        → 调用方落在 dynamicJS 的 pe.*.js 里，但断点命中的位置"每次都不一样"
步骤 3：判断这不是普通函数，是解释器 → 找它的 opcode 表
        → 反汇编出 56 个 opcode，再反汇编两段字节码：
          一段很长（生成 nonce），一段很短（做加密层）
步骤 4：dump 解释器的常量池
        → 拿到一个 16 字节 hex 种子 + 一张 64 项的表 + 一段自修改循环
```

**怎么确认它是"查表变换"而不是加密算法**：

- 输出长度与输入长度**严格相等**（没有任何分组/填充特征）
- 变换过程中表自身被 swap 修改（自修改），状态由两个索引 `e/a` 自推进
- 没有任何密钥参与——只有一个构建期常量种子

**怎么验证解对了**（这一步最重要，别跳过）：

| 验证项 | 方法 | 结果 |
|---|---|---|
| 正向复算 | 取两组**同一会话**的真实样本，用解出的算法重算 `data` | 逐字节 0 差异（0/524、0/536） |
| 可逆性 | `unarmour(armour(T)) === T` | 2/2 成立 |
| 结构自洽 | `|enc|` 应等于 `|T|`（不是 −3，也不是 4/3） | 成立 |

> **"同一会话的两组样本"是这里的关键**。我早期用的是互不相关的两个样本，相关性只有 1.2%，
> 因此把所有"密钥流"结论都推翻了。要验证一个编码层，样本必须能配对。

### 三、几何：别信直觉，做受控标定

直觉会告诉你"拖多少块就走多少"。实际不是。

做法是**受控拖拽**：固定指令走 600px，读块的实际位移，重复 6 次取均值。

```
结论：块位移 = 手指位移 / 常数（该站点是 2.5，6 个样本 2.50±0.005）
图片 296×200 渲染成 750×500（容器 transform: scale(2.5)）
→ slidePos = 手指位移/缩放，xPos = 块最终位置/缩放
```

> ⚠️ 有公开项目在另一处集成里测出**二次关系**（`piece.left = A·m + B·m²`）。
> **换站点必须重新标定，不要照抄系数**——同一厂商不同集成方式的映射可以完全不同。

### 四、12 次失败：把范围一步步收窄

拿到"能离线生成合法 data"之后，我以为就成了。结果是连续的 false。

于是按控制组的思路逐项排除，**每一项都单独跑过**：

| # | 假设 | 怎么排除的 | 结果 |
|---|---|---|---|
| 1 | `data` 算错 | 两组真实样本逐字节比对 + 往返可逆 | 排除 |
| 2 | 缺口几何错 | 闭环把块对齐到 **0.24 CSS px** | 排除 |
| 3 | `certifyId` 过期 | 3.1 秒内提交 | 排除 |
| 4 | 轨迹被判"不可信" | 换真鼠标注入，`isTrusted` 全 true、标记位全 1 | 排除 |
| 5 | 请求上下文不对 | **页面自己发 XHR**（不经过我的代码） | 排除 |
| 6 | 设备遥测断链 | 换全新 profile 后遥测 200、`ResultObject:true` | 排除 |

第 6 条当时是个假象，值得单独说：

> 脚本里 `tempfile.mkdtemp = lambda: PROFILE` 把所有轮次钉在同一个 profile 上，
> device SDK 的本地状态累积后，遥测请求变成 `status 0`。
> **看起来像风控拒绝，其实是自己把会话写脏了。** 换全新 profile 立刻恢复 200。

排除完六项，我做了个"极限实验"——把所有可观测指标都对齐到真人：

```
529 点 / 跨度 5119ms / dt 中位 6ms / 标记位全 1 / 对齐误差 1.47 CSS px
xPos 与 slidePos 也和真人那次几乎相同
```

**仍然 false。** 到这里我才敢说：门槛不在这些可观测维度上。

### 五、翻转：真正缺的是"像不像人"

转折来自对照公开实现。有人用 30 条真人轨迹 + 合成轨迹训了个分类器，**AUC=1.000 完美可分**——
结论是：教科书式的平滑曲线本身就是机器指纹。

真人轨迹的真实形态是四段：

```
慢逼近（占 45~60% 的帧，只走 15~30% 的距离）
→ 谷底犹豫（3~6 帧，微位移 + dt 40~110ms，在"看缺口"）
→ 末端甩鞭（16~28 帧吃掉 86~94% 的距离，峰值速度 9722 px/s @ 74.5% 进度）
→ 收尾（5~10 帧，dt 6~16ms）
```

配套的九项指纹（这才是可验收的部分）：

| 特征 | 真人数值 | 平滑曲线（机器） |
|---|---|---|
| 峰值速度位置 | **74.5% 进度** | 5~20% |
| 峰值速度 | **9722 px/s** | ~1400 px/s |
| 每步 `dx` | **中位 1px**（p90 2px） | 大步长 |
| 完全静止帧 | **4%** | 0% |
| 中段回拉 | 1~3 次，0.8~2.2px | 无 |
| 末端回拉 | **55% 概率，3~12px** | 无 |
| y 路径 std | **38px（手臂线性漂移）** | 2px 抖动 |
| 事件数 | **127**（p10~p90 86~215） | 数百上千 |
| 总时长 | **1.62s** | 数秒 |

按这个重写轨迹生成器后，**5/5 连续通过**（缺口 160~202，帧数 92~114，时长 0.88~1.24s）。

### 六、这一轮我判断错的三次（都有判据，写下来给后来者）

1. **「点数越多越像人」是错的**——生成 543 点 / 4.4 秒全 false，92 帧 / 0.88 秒通过。
   点数是**噪声**，形态才是信号。
2. **一度判定「必须真人手拖 / 必须硬件设备」**——错的。纯软件注入 5/5，
   之前的失败纯粹是形态错。**这个结论一旦写进报告，就等于给后来者判了死刑。**
3. **在浏览器里调注入工具的坐标**（按下抓不住滑块之类）**是跑偏**。
   纯协议根本不需要浏览器；先把数据层离线复现，再谈输入。

## 加密方案（结构性描述）

```
payload = nonce(hex, 32 字符) ‖ JSON{TrackList, TrackStartTime, VerifyTime, xPos, slidePos, arg}
T       = base64( zlib.deflate(payload, level 6) )     // T 恒以 "eJ" 起步
data    = base64( armour(T) )                          // 与 T 等长；前 3 字节是产物不是常量
```

`armour` 的结构（不给具体常量）：

1. 用**构建期常量种子**（16 字符 hex）把一张 **64 项置换表**打乱；
2. 逐字符变换：两个索引 `e/a` 自推进，每次迭代都对表做一次 swap（**自修改**），
   再做若干异或与加法组合；
3. 因为 `T` 恒以 `eJ` 起步，前几个字节的输出自然固定——**这就是那个"魔数"的来源**。
   它不是常量，所以静态搜魔数永远搜不到。

**没有密钥**。设备配置里那个每会话变化的 key 不参与这一步，别被它带偏。

## 关键判据（可直接复用）

**加密层**

```
1. 输出长度 == 输入长度 → 大概率是查表/置换类，不是分组加密
2. 变换过程中表自身被修改 → 自修改，样本必须**同轮配对**才能验证
3. 前 N 字节"恒定"要先验证是不是产物：改变输入首字节，看它是否跟着变
4. 验证必做两件事：正向逐字节复算 + 反向可逆
```

**轨迹形态**

```
1. dx 不应出现大幅负值：真人全程单调，末段才有 6~13 帧小额回拉（3~12px）
   出现 ±30px 级正负交替 = 脚本特征
2. dx 中位应在 1px 量级（p90 ≤ 2px），不是大步长
3. 峰值速度必须出现在 60% 进度之后；出现在前 20% 就是"前载爆发"，机器特征
4. 必须有 3~7% 的零位移帧（真人会顿一下）
5. y 是**缓慢线性漂移**（几十 px 量级）+ 温和振荡，不是白噪声抖动
6. 落点靠轨迹设计（贝塞尔终点=目标），不要"边拖边按块的实时位置回压手指"
   —— 那样会形成正反馈震荡，屏幕上就是指针来回乱抖
```

## 踩坑清单

| 坑 | 教训 |
|---|---|
| 以为魔数是常量，静态搜 | 它是 SEED 固定 + 输入首字节固定共同算出来的**产物** |
| 把 `|enc|` 读成 `|T|−3` 或 4/3 膨胀 | 实际严格等长，多出来的 3 字节就是输出的前缀 |
| 用两个互不相关的样本验算法 | 相关性 1.2%，所有"密钥流"结论全部作废；必须**同轮配对** |
| 复用同一个浏览器 profile | device SDK 状态累积 → 遥测 `status 0`，看起来像风控拒绝，其实是自己写脏了会话 |
| 把轨迹末段那个 100+px 的跳变当"异常尾巴" | 那正是**末端甩鞭**，是真人最显著的特征 |
| 用闭环"按块的实际位置回压手指" | 造出正负交替的震荡轨迹，真人不会这样 |
| 在浏览器里调注入工具的坐标/焦点 | 跑偏；纯协议不需要浏览器 |
| 认定"必须真人/硬件设备" | 错，是形态问题 |
| 忽略 JPEG/PNG 之外的噪声（如 `WebGL context was lost`） | SDK 正常行为，不是失败原因 |
