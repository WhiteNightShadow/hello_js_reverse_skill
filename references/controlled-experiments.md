# 对照实验与归因

在线目标是黑箱，而且每次试错都有成本：账号额度、一次性值和风控状态都会被消耗，失败还会污染后面的判断。在线实验的目的不是多试几次，而是用尽量少的请求排除假设。

本文只讲实验方法，与具体站点无关。文中的阈值、次数都要按当前项目实测确定。

## 动手前写实验单

| 字段 | 内容 |
|---|---|
| 问题 | 这组实验只回答一个问题 |
| 预期分叉 | 结果 X 说明什么，结果 Y 说明什么 |
| 固定项 | 已固定的字段及来源 |
| 变量 | 这次唯一改变的内容 |
| 未固定项 | 明知控制不了的东西，如服务端状态、SDK 内部缓存、批次间变化的 Cookie |
| 预算 | 本批请求上限 |
| 停止条件 | 哪些结果立即停止 |

写不出“结果 X 说明什么”时，这个实验不该发。模板见 `templates/param-tracking/experiment-sheet.md`。

## 在线门禁

每次发送前检查，任何一项不通过就不发，并记为 `not_sent`：

1. **版本一致**：页面此刻实际加载的 SDK 与本地一致。页面可能在实验中途换版。
2. **时效余量**：Cookie、令牌、验证证书到期前留足本批所需时间。实验跨过到期点后无法归因，这类失败不能算候选失败。
3. **值未使用**：一次性值确实没有发出过。
4. **输入成套**：快照、模板、Cookie 来自同一时刻的同一页面，缺项时停止，不用空值代替。
5. **预算与停止**：本批未超预算，也没有未处理的拒绝。
6. **离线校准**：浏览器和本地都能导出内部产物（初始化后的表、常量样本）时，先逐字比较，不一致就不发。这比在线请求便宜得多。

```bash
python scripts/experiment-ledger.py gate --ledger runs/ledger.jsonl --batch 20261105-a --budget 3
```

## 标准三组

要判断“本地值能否替代真实值”时使用：

| 组 | 非动态字段 | 动态值 | 回答的问题 |
|---|---|---|---|
| A | 真实请求的全部字段 | 真实新值 | 此刻基线成立吗 |
| A2 | 冻结 A 的模板 | 新的真实值 | 冻结模板本身有问题吗 |
| B | 冻结同一模板 | 本地值 | 本地值能替代真实值吗 |

- 按 A、A2、B 的顺序执行，前一组失败就不做后一组。未执行记 `not_sent`，不算失败。
- 三组放在同一批次内。跨批的 Cookie、令牌可能已经变化，不能直接比较。
- B 比 A2 多用一次模板、晚几十秒时，复用和时间也成了变量，要单独隔离（见下文）。

判读表在 [问题路由](problem-routing.md#链路-b服务端拒绝)。

## 控制组失效

控制组失败时，这批实验没有归因价值，不能写“候选失败”。

1. 停止本批。
2. 确认页面正常操作产生的真实请求是否可用，区分“账号此刻所有路径都不行”和“只有构造路径不行”。
3. 恢复后新建批次重做。

控制组失败本身也有信息量。完整真实路径也失败时，“冻结模板导致失败”就不成立了。

## 单变量要回读

“只改了 X”要用实际发出的请求核对，不能看脚本意图。常见漏洞：

- 每次都重新生成的字段（随机串、时间戳）在两组里不同，而报告里没提。
- 负对照沿用了前一组已发送的另一个一次性字段。
- HTTP 客户端自动补头、改写大小写或顺序。
- 辅助函数内置重试，实际尝试数未知，这时结果只能写“次数未知”。

```bash
python scripts/experiment-ledger.py audit --base runs/a2.private.json --candidate runs/b.private.json \
  --allow x-sign --allow x-ts --must-change x-sign
```

输出只含哈希和长度，不含原值。出现 `unexpected` 就不能写“单变量”，按实际差异收窄结论。完整请求保存在私有目录，否则事后无法核对。

## 单变量没有翻转时

服务端可能有两道互相独立的闸门，任一不过都返回同样的拒绝。这时只改一项看起来“没有效果”，真实原因就容易被排除掉。看到“改了 A 没变化”，先问是不是还有 B 堵着。

用交叉矩阵代替单向对照。以值和发送通道为例，四格都做：

| | 真实新值 | 本地值 |
|---|---|---|
| 页面通道 | 控制组 | 反向对照 |
| 本地客户端 | 正向对照 | 候选 |

| 正向对照 | 反向对照 | 判读 |
|---|---|---|
| 成 | 败 | 问题在值 |
| 败 | 成 | 问题在传输 |
| 败 | 败 | 控制组成立时，两道门都没过 |
| 成 | 成 | 单项都没问题，候选仍失败就查组合，如请求形态和绑定关系 |

- 实验客户端用生产实际使用的客户端。两个恰好都能过的客户端对那道门没有分辨力，会得出“这个因素无关”的错误结论。
- 反向对照走页面通道时注意 [再次签名](signature-source-isolation.md#避免再次签名)。
- 其他因素对（UA 与 TLS、账号与出口）同样可以交叉。

## 结果时好时坏

同一构造跨次翻转，说明判定可能是概率性的，单次拒绝或单次成功都不能归因。

- 单独开稳定性批次，事先写明次数和预算。
- 报成功数和翻转数，不报单点。样本不足不判方向，阈值按项目定，别处的数字不要照抄。
- 重测全部固定样本，不要只复测上次失败的。
- 探索批遇拒绝就停。稳定性批是预先声明的计量批，拒绝不中止，但出现频控或账号受限信号时立即停。

```bash
python scripts/experiment-ledger.py gate --ledger runs/ledger.jsonl --batch stability-1 --budget 10 --allow-rejections
```

## 测量手段先过对照

“没有差异”可能只是工具看不见。比较之前先确认测量本身可信：

- **A/A**：同配置连测两次，标出本来就变的字段，这些字段不作判据。
- **阳性对照**：故意改一个已知会变的设置，确认这条路径看得见变化。
- **折叠随机部分**：比较前去掉随机数、公钥字节等每次都变的内容。

这条同样适用于 Hook、Trace、回读和传输特征抓取。

## 时间、复用和顺序是独立变量

这几项经常被混成一个“失败原因”，要分开记录：

| 变量 | 记录什么 | 容易犯的错 |
|---|---|---|
| 值的年龄 | 生成到发送的间隔 | 把“距首发时间”当成值的真实年龄 |
| 复用次数 | 同一模板或值发过几次 | 第三次失败时只看到“第三次” |
| 批内顺序 | 这是本批第几个请求 | 把后发请求的失败归因给候选 |
| 请求间隔 | 与上一次的间隔 | 触发频控后归因到签名 |

用一组只改一个维度的实验隔离。例如三次都用新真实值、冻结其余字段，就能回答“冻结到第三次是否必然失败”。

## 结果分类

失败不是一种东西。合并记录会让后面的判断建立在错误事实上。

| 分类 | 含义 | 不能写成 |
|---|---|---|
| `not_sent` | 门禁或预检拦下，请求没发出 | 失败 |
| `transport_error` | 超时、连接错误，服务端是否收到未知 | 被拒绝 |
| `rejected` | 服务端明确拒绝，含 HTTP 200 内的业务错误 | 签名错 |
| `accepted` | 未被拒绝，但目标断言未通过或未断言 | 成功 |
| `target_ok` | 到达 S3 | 稳定可用 |

## 结论强度

| 用词 | 条件 |
|---|---|
| 观察到 | 有记录，没有对照 |
| 支持 | 对照方向一致，但还有未固定变量 |
| 排除 | 单独改变这个条件不足以翻转结果。这不代表它不用修，并联闸门下可能仍要修 |
| 证明 | 控制组有效、回读确认单变量、结果可重复 |
| 未验证 | 没有实际跑过 |

“排除”和“证明”都只对当时的版本、接口和会话成立，日期要写进结论。结论的依据是另一个维度，见 [结论怎么写](version-tracking.md#结论怎么写)。

## 差异、读取、校验是三回事

看到两边不同，不代表 SDK 读了它；SDK 读了，不代表服务端校验它；修了它之后成功，也可能是同时修的别的东西起了作用。这三级证据要分开写，见 [原始 SDK 运行](original-sdk-runtime.md#读值差异)。

## 负对照

负对照证明判据有区分力，比如用已用过的值，确认服务端确实会拒绝。它消耗请求且可能触发风控，放在正对照成功之后，做一次就停。负对照同样要满足单变量，否则只能写“支持方向”。

## 组合成功不等于单项根因

一次改了多项之后成功，能证明的是“这个组合成立”。归因到其中某一项需要消融实验。业务不需要时可以不做，但结论里不能写成某项修好了问题。SDK 升级和环境修复同时发生时尤其如此。

## 预算与停止

- 一批次回答一个问题。
- 遇到拒绝就停止当批，保留请求形态和会话证据。
- 继续发请求前，要能说清这次和上次差在哪、预期结果是什么。说不清就回到离线分析。
- 不用加速、并发或重试碰运气。这样既得不到结论，也可能把账号或会话推到更差的状态。

```bash
python scripts/experiment-ledger.py record --ledger runs/ledger.jsonl --batch 20261105-a \
  --variant B --outcome rejected --evidence runs/b.response.private.json --note "只换本地值"
python scripts/experiment-ledger.py summary --ledger runs/ledger.jsonl
```

本批出现 `rejected` 后，`gate` 会阻止继续。开启新批次是一个有意识的决定，新批次要有新假设。

## 证据落盘

```text
runs/<YYYYMMDD-HHMMSS-主题>/
├── sheet.md               # 实验单
├── ledger.jsonl           # 每次尝试的分类
├── *.private.json         # 完整请求、响应、会话，权限 0600，不入库
├── audit.json             # 回读结果，只含哈希
└── summary.json           # 脱敏摘要
```

保留失败批次和未发送批次。后续实验新建批次，不覆盖最后成功的证据。

## 结论写错了怎么办

不改写原始证据，在结论处加日期化的纠偏：原说法是什么、哪份证据推翻了它、现在的强度是什么、哪些结论不受影响。最后一项不能省，否则读者会把仍然成立的正结果一起否定。历史判断里“唯一”“必须”“硬墙”这类词最容易过期，写结论时避开它们，改写成带范围的观察。
