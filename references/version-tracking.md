# 参数跟踪与版本归档

长期维护一个采集目标时，最贵的不是写代码，而是几周后分不清哪些结论还成立。本文给出一种按版本归档的方法，适用于任何需要持续跟踪的签名或动态参数。模板在 `templates/param-tracking/`。

## 身份分开记录

这些东西都叫“版本”，但互相推不出来：

| 身份 | 来源 | 用途 |
|---|---|---|
| SDK 文件名与 SHA-256 | 页面实际加载的资源 | 唯一可靠的代码身份 |
| SDK 公开版本 | 源码内版本字符串 | 版本目录名 |
| 请求头声明版本 | 实际请求头 | 只说明这个头的值 |
| 协议标记 | 令牌内魔数等 | 判断外层是否换代 |
| 运行时版本 | 依赖清单 | 复现环境 |
| 实现修订 | 自己代码的修订名和提交 | 同版本 SDK 下的实现变化 |

- 版本未知就写“未确认”，不从请求头或魔数反推。
- 代码里的兜底默认值不是版本证据。
- CDN 路径里的地区或目录名不代表业务地区。
- 同一 SDK 下的环境或初始化改造记为实现修订，不能写成 SDK 升级。

```bash
python scripts/project-baseline.py create --root . --files sdk/a.js fixtures/ok.json \
  --identity sdk_public=<版本> --identity protocol_marker=<标记> --identity impl_revision=<修订名>
python scripts/project-baseline.py check --root .
```

## 目录结构

```text
<目标>/
├── README.md              # 当前路线、接口、成功判据、验收边界
├── change-log.md          # 版本差异表 + 定位过程表
└── <SDK 版本>/README.md   # 来源、哈希、入口、输入输出、实验、证据、限制
```

- **入口页**回答：这个接口做什么、当前走哪条路线、成功判据是什么、已验证到哪一层。
- **版本页**写来源 URL、文件、完整 SHA-256、模块入口、输入输出、定位过程、实验结果和限制。
- **变更记录**写日期、前后版本、文件或哈希、实现变化、请求形态、验收结论和替代关系。
- SDK 升级时新建版本目录。同版本文件哈希变化时保留前后身份，不覆盖旧证据。
- 原始 SDK、Cookie、令牌和响应留在本机私有目录，文档只写位置和哈希。证据文件缺失时要从原批次恢复，不拿脱敏说明当可重放输入。

## 结论怎么写

结论带适用范围，读者才能判断还能不能用：

```text
结论：<一句话>
范围：<接口> / <SDK 版本与哈希> / <观测日期> / <账号或会话状态>
层级：S? ；强度：观察 / 支持 / 排除 / 证明
依据：来源转述 / 静态阅读 / 运行时观察 / 本地等价 / 服务端接受
未验证：<多目标、连续、续期、跨天等>
失效条件：<什么变化后要重验>
```

强度回答“对照有多严”，依据回答“谁在哪一层看到的”，两个维度不能合并，也不设全局的“已验证”。来源作者说成功，只能记来源转述，不因文章写了成功而升级。未知项写未知，不用归档日期代替观测日期。结论多时给每条编号，新结论写明替代哪条，旧结论保留。

几个容易写错的地方：

- 按接口写，不按“站点”写。同一站点不同接口、不同端的闸门可以不同。
- 历史观察加日期。“某头可选”只是当时某接口的观察，以后可能变成闸门。
- 服务端策略可以在 SDK 不变时改变。哈希未变不代表行为未变。
- 最终实现精简后，用保存的请求和响应做离线等价检查，不能把它写成新的在线验收。

## 固定迭代步骤

每轮都走这五步，每步写清命令、产物位置和判据：

| 步骤 | 做什么 | 判据 |
|---|---|---|
| capture | 采样本和控制组 | 样本完整，控制组到 S3 |
| analyze | 解码、对比基线 | 结构对得上或差异已记录 |
| generate | 生成候选值 | 通过 S1 检查 |
| validate | 有界在线验证 | 到达目标层级，或失败已分类 |
| log | 写结论、归档证据 | 同一事实只落一处，其余用链接 |

## 纠偏

发现旧结论写错时，在原处加日期化说明：原说法、推翻它的证据、现在的强度、哪些结论不受影响。原始脚本和响应保持不变。把错误结论悄悄改掉，后面的人就不知道哪些判断曾依赖它。

## 换版回归

1. 保存新 SDK 与哈希，核对页面实际加载的 URL 和协议标记。
2. 恢复成功控制组，再试本地候选。
3. 快照和请求成套新鲜，缺失不用空值代替。
4. 离线通过只说明本地兼容，在线要重新断言业务字段。
5. 保留最后成功批次，新实验新建批次。

旧版本的内部追踪结论不能无条件沿用到新版本，要写明哪些是继承的假设、哪些是重新验证的事实。
