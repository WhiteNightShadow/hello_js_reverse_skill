# 问题路由：遇到什么问题，走什么链路

本文是 Skill 的主干，只讲判断顺序和收口标准，不含任何站点规则。站点、SDK、参数名和错误码只出现在 [cases](../cases/README.md) 与需求工作区。案例命中只产生候选假设，走哪条路由当前目标的证据决定。

## 三个基本判断

### 一、成功分四层，下层推不出上层

| 层级 | 含义 | 算数的证据 | 不算数的证据 |
|---|---|---|---|
| S1 能生成 | 本地产物结构合法 | 格式、校验位、长度范围通过 | “能跑出一个值”本身 |
| S2 被接受 | 服务端没有拒绝 | 无业务错误码、未跳错误页 | HTTP 200 |
| S3 命中目标 | 响应正是请求的那份数据 | 目标 ID、关键字段、地区或币种断言；可疑时比较跨运行是否一致 | 响应非空、结果看起来合理 |
| S4 可持续 | 多目标、连续、续期、跨天都成立 | 按业务约定的批次实测 | 单条成功、离线等价 |

汇报写到实际到达的层级。这样分的原因是：外层校验全过的值仍可能被拒，被接受的请求仍可能返回错目标，单条成功也不代表第二天还成立。

### 二、失败分六层，先定层再动手

| 层 | 要回答的问题 | 容易混进来的现象 |
|---|---|---|
| 传输 | 包到了吗？客户端特征被区别对待了吗？ | 超时、代理、证书、TLS、HTTP/2 |
| 会话 | 凭据此刻有效吗？绑定了什么？ | Cookie、令牌、验证证书到期 |
| 请求形态 | URL、方法、参数、头集合和顺序对吗？ | 多发或少发字段、编码差异 |
| 动态值 | 时效、一次性、来源对吗？ | 重放已用值、过期值、本地值 |
| 运行环境 | SDK 读到的环境和状态与基线一致吗？ | 缺 API、缓存、初始化顺序 |
| 服务端策略 | 账号、频率、额度、风控状态如何？ | 代码之外的原因 |

服务端策略只能从响应侧间接观察，所以放到最后排除。同一个现象（403、空数据、错误码）可能来自任何一层，现象本身不定层，对照实验才定层。

### 三、诊断从重到轻，交付从轻到重

诊断时先用最接近真实、依赖最多的路径证明“这件事此刻做得成”，再一次拿掉一个依赖，每拿掉一个就重新验证。第一个让结果变坏的依赖就是问题所在。

交付时选能成立的依赖最少的路线。两个方向不矛盾：诊断要的是确定性，交付要的是低成本。直接从最轻的路线开始试，失败时分不清是路线不对还是基线本来就坏了。

## 路线阶梯

| 路线 | 做法 | 主要依赖 | 停在这里的条件 | 上移的信号 |
|---|---|---|---|---|
| R0 不生成 | 接口不校验这一项，直接不发 | 无 | 删减实验后 S3 仍成立 | 换接口或换日期复验失败 |
| R1 纯算法 | Node/Python 库复现 | 语言标准库 | 固定输入逐字一致，且新输入到 S3 | 算法依赖闭包状态或环境 |
| R2 片段执行 | 提取函数放进 vm/execjs | JS 运行时 | 片段自洽且到 S3 | 依赖 DOM、存储或大量全局状态 |
| R3 补环境 | jsdom/vm 运行 SDK，按读值补齐 | 补丁维护成本 | 补丁面小且到 S3 | 补丁不收敛，或静态值对齐后仍被拒 |
| R4 浏览器级运行时 | 真实 JS 引擎和原生 API 运行原始 SDK | 运行时与外部状态输入 | 状态可获得且到 S3 | 所需状态只存在于真实长驻页面 |
| R5 页面出值、本地发送 | 真实页面生成未使用的值，本地 HTTP 发送 | 常驻浏览器 | 成本可接受 | 传输确实绑定页面 |
| R6 页面内请求 | 请求由页面自身发出 | 浏览器 | 用户明确接受此依赖 | 无 |

- 默认交付目标是 R0～R2 的无浏览器协议程序，但能否到达由证据决定。
- R5 同时是诊断基线：即使最终目标是 R1，也值得先用它证明上限。
- R4、R5 仍依赖外部提供会话，交付说明要写清谁提供 Cookie、谁负责续期，不能写成“无浏览器”。
- 不必为了“还原算法”而还原。目标是取得可用的值，只有业务需要脱离运行时才值得继续下探。

运行时候选见 [原始 SDK 运行](original-sdk-runtime.md)。

## 链路 A：这个参数到底要不要算

**入口**：请求带 sign、token 或自定义头，还没开始逆向。

1. 取一条成功请求原样重放。重放失败说明含一次性值或时效值，转链路 C。
2. 按组删减：先去掉疑似签名组，再减 Header，再减 Cookie。一次只动一组并记录结果。
3. 删掉后仍到 S3，走 R0，不做逆向。只在部分接口需要时，按接口记录。
4. 不把同站其他端、其他接口的结论带过来。不同接口的闸门可以不同，别处必需的头在这里多发也可能被拒。

**收口**：最小字段集、成功样本、适用范围（接口、版本、日期）。这类结论会过期，服务端可以在 SDK 不变时收紧校验。

## 链路 B：服务端拒绝

**入口**：HTTP 4xx，或 HTTP 200 内带业务错误码、空数据、错误页跳转。

1. 先分类结果。超时、未发出和拒绝是三件事，分类见 [对照实验](controlled-experiments.md#结果分类)。
2. 恢复控制组：用页面自身路径拿到一次 S3。控制组失败就停止归因，转查会话、账号和频控，此时候选的结果无效。
3. 做来源替换，详见 [对照实验](controlled-experiments.md#标准三组)：

| A 完整真实请求 | A2 冻结其余字段，只换新的真实值 | B 冻结其余字段，只换本地值 | 判读 | 下一步 |
|---|---|---|---|---|
| 成 | 成 | 败 | 问题在本地值 | 链路 E |
| 成 | 败 | 不必执行 | 冻结字段有时效或配对关系 | 查时序、复用和绑定 |
| 败 | 不必执行 | 不必执行 | 控制组失效 | 回到第 2 步 |
| 成 | 成 | 成 | 之前的失败来自会话或时效 | 查门禁记录 |

4. 用实际发出的请求核对“只换了声称的变量”，再写结论。

**收口**：写明结论强度（观察、支持、排除、证明）和仍未固定的变量。

## 链路 C：浏览器能过，本地同样的头不过

**入口**：把页面发出的头复制到本地失败。这时最容易直接归因到 TLS，但应按代价从低到高排除：

1. **值已用过或过期**。已发出请求里的值可能是一次性的，改用未使用的值，见 [签名来源隔离](signature-source-isolation.md)。
2. **会话差异**。检查 HttpOnly Cookie、验证证书是否跨过到期点，用浏览器原生 Cookie 导出，不用 `document.cookie`。
3. **请求形态**。逐字节比较头集合、顺序、大小写、编码和 Body 原文。
4. **传输**。把未使用的值分别走干净页面通道、TLS 模拟客户端和普通 HTTP 客户端，再做反向对照：本地值走页面通道。只有这组对照出现稳定分界，才能说是传输层，方法见 [协议层分析](protocol-analysis.md#传输层诊断实验)。

单项都没有翻转时不要逐个排除，可能是两道闸门并联，用 [交叉矩阵](controlled-experiments.md#单变量没有翻转时)。

**收口**：写明是哪一组对照给出分界。没有分界就不写传输结论。

## 链路 D：之前能用，现在不行

**入口**：历史成功的代码或样本失效。

1. 核对页面此刻实际加载的 SDK（URL、哈希）与本地是否一致。不一致就先同步，这一步放在首条在线请求之前。
2. 从最后成功的基线回归，而不是从当前失败的版本继续改。
3. SDK 变了：新建版本记录，从链路 A 重走，旧结论不自动继承。
4. SDK 没变但行为变了：服务端策略变化，历史结论按日期失效。
5. 保留旧证据，见 [参数跟踪](version-tracking.md)。

**收口**：差异记录写清前后版本、请求形态、验收层级和替代关系。

## 链路 E：本地值能生成，但不被接受

**入口**：链路 B 已把问题定到本地值。

1. 确认入口。页面真实路径调用的入口与本地调用的是否相同；多个入口时比较中间值，一致就不必换入口。
2. 做读值差异。记录 SDK 实际读取了什么、基线读到什么、本地读到什么，分清三级证据：观察到差异、SDK 实际读取、服务端确实校验。
3. 查生命周期。SDK 可能在首次读取后缓存，用哨兵实验确认，再决定 seed 时机和实例粒度。
4. 按读值证据组合修复，先离线检查和校准内部产物，再有界在线验收。
5. 组合成功就写“组合成立”。业务需要稳定性或成本优化时才做单项消融。

**收口**：到 S3 的组合、依赖的外部输入、未复原的状态。细节见 [原始 SDK 运行](original-sdk-runtime.md)。

## 链路 F：SDK 在本地跑不起来

**入口**：加载或调用报错，例如 `undefined.call`、构造器缺失、`null` 上取属性。

1. 沿调用链定位真实缺口，不要只看报错行。VM 内的报错常是几层之后才暴露，最初的猜测经常被实参插桩推翻。
2. 只补被证实读取的对象，并按真实结构补（原型链层级、构造器名、方法挂载位置）。
3. 补丁持续不收敛时，上移到 R4，不要继续堆补丁。“不收敛”指连续几步都没有新证据，步数写进实验单。普通 JS 表达不了的语义（如 `document.all`、realm 差异）也是上移的信号。
4. 跑通只到 S1，接下来走链路 B。

**收口**：缺口清单和对应证据。

## 链路 G：混淆或 VM 挡住定位

**入口**：看不懂签名逻辑。

1. 先问需不需要看懂。入口能调用、原始 SDK 能运行时，可以不读内部。SDK 加载后枚举一次非内建的全局符号，导出函数常常能直接跳过 VM。
2. 需要还原算法时先定位 I/O 边界，再决定静态还原、Hook、源码插桩或环境复现，见 [深度分析流程](phase-details.md)、[路径 A](path-a-four-tools.md)、[路径 B](path-b-env-emulation.md)。
3. 服务端每次下发不同的混淆代码时，静态还原的成果留不下来，优先运行它（R2、R3）。
4. 反混淆产物按 [改写验证](transform-validation.md) 比较行为，可读视图不等于等价代码。
5. 值带随机掩码、无法逐字比较时，转 [不透明令牌分析](opaque-token-analysis.md)，用结构和业务结果判断。

**收口**：选定路线和不选其他路线的证据。

## 链路 H：单条成功，批量失败

**入口**：已到 S3，扩大范围后开始失败。这是 S4 问题，通常不是算法问题。

1. 先看失败和什么相关：次数、时间、账号、目标、会话年龄。
2. 按一次性值、频控、会话衰减、目标差异分别隔离，一次只放大一个维度（先多目标，再连续，再跨天）。
3. 头几发正常、之后开始拦，可能是上报后异步判定，不一定是累积风险或指纹变化。时好时坏时开 [稳定性批次](controlled-experiments.md#结果时好时坏)。
4. 遵守业务冷却和停止条件，拒绝时停止当批，不靠加速或重试碰运气。

**收口**：按多目标、连续、续期、跨天分别标状态，未跑过的写未验证。

## 链路 I：观测本身有问题

**入口**：Hook 没日志、插桩后行为变了、样本被污染。

1. 空结果不是否定证据。先查 world、Frame、容量和覆盖范围，见 [浏览器取证契约](browser-evidence-contract.md)。
2. 原始和插桩各跑一次，比较请求方法、URL、头、Body 长度、响应、异常、调用顺序和次数，不只比最终值。结果记为一致、被干扰或未知，有未比项就是未知。一致也只说明已比较的范围。
3. 观察环境和产值环境分开。包装原生方法可能污染持久化状态，换干净环境才能恢复。
4. 观测导致的超时或异常不能推断目标有反 Hook 检测。

**收口**：说明观测手段的覆盖范围和可能的干扰。

## 链路 J：慢

**入口**：单条耗时不符合预期。

1. 拆开调度等待、运行时初始化、出值、网络和解析，分别计时。
2. 调度冷却不是接口耗时，业务冷却不因实现变快而调整。
3. 优先复用上下文和连接，再看是否能减少无用初始化；复用前确认 SDK 没有一次性状态。

**收口**：分段耗时表，优化前后同条件对比。

## 链路 K：频控、验证或账号受限

**入口**：429、验证页、账号或会话被限制，或原本成功的路径整体变差。

1. 停止当批，保留响应和会话证据。继续请求只会让状态更差。
2. 用最少的请求确定影响范围：是这个账号、这个出口、这个会话，还是所有路径。
3. 是否出现验证由目标站决定，不做本地预判。恢复走业务认可的流程，这一步要用户参与时就交给用户。
4. 恢复后用原目标复验。页面看起来正常、验证通过都不算恢复，到 S3 才算。
5. 调整节奏和批量，遵守业务冷却。不靠绕过或换身份碰运气。

**收口**：触发条件、影响范围、恢复方式和复验结果。

## 收口格式

任何链路结束时都写下面五项，下一个接手的人才能判断结论还能不能用：

```text
到达层级：S?（列出未到的层级）
当前路线：R?，外部依赖：谁提供会话、谁续期
适用范围：接口 / SDK 版本与哈希 / 日期 / 账号或会话状态
结论强度：观察 / 支持 / 排除 / 证明，仍未固定的变量
失效条件：什么变化后这条结论要重验
```
