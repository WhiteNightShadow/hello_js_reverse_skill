# 不透明令牌分析：信封、版式与批次对比

适用于值带随机掩码、无法逐字比较，或想知道一个长令牌的结构时。这里的目标是获得足够做决策的结构信息，不是把内层字段全部解开。

## 什么时候做

- 要判断“这个值变了没有”“换版了没有”“长度异常是否正常”。
- 要写 S1 校验（本地值结构是否合法）。
- 要决定是否值得继续深挖。

已经能用运行原始 SDK 的方式到 S3 时，内层字段解码可以暂缓。

## 先设计样本批次

一批样本要有受控的差异，否则对比没有意义：

| 变化维度 | 回答的问题 |
|---|---|
| 同一环境，连续多次 | 哪些字节每次都变 |
| 同一环境，重启或隔天 | 是否有时间相关的轮换 |
| 不同账号或环境 | 是否与设备、账号相关 |
| 不同接口 | 是否与 URL 或请求内容相关 |
| 不同 SDK 版本 | 结构是否改版 |

样本落盘时脱敏，记录时间、环境、接口和批次目录，与其他批次对比时写明基线。

## 外层：编码与校验

```bash
python scripts/opaque-token-inspect.py samples.txt
python scripts/opaque-token-inspect.py samples.txt --encoding base64
python scripts/opaque-token-inspect.py samples.txt --encoding custom --alphabet '<64 字符表>' --xor-align
```

1. 看字符集和长度：是否 4 的倍数、有无 `=`，判断 hex、标准 base64、url-safe 或自定义字符表。
2. 自定义字符表可从 SDK 源码常量找到。解码后多条样本应呈现稳定位置。
3. 单字节异或这类按请求变化的掩码，`--xor-align` 会逐条寻找使样本与基准最一致的 key。已知 magic 时可穷举 key 对上它；未知时可用校验位自验证：对每个候选 key 复算校验，能通过的就是当次 key。
4. 找到稳定头部后，判断魔数、长度字段（值等于 Payload 长度）、校验位（复算一致）。
5. **固定前缀未必是源码字面量**：若解码后前几个字节跨样本恒定，但全局静态搜不到对应常数，先检查是否为「固定初始状态 + 固定明文头（如 `zlib`/`gzip` 压缩头或固定键名前缀）」经确定性流式/查表变换自然产生；改输入首字节即可验证前缀是否随之改变。
6. **等长无填充密文的分支判断**：输出与输入字节数严格相等且不按 8/16 字节块对齐时，除标准流模式（CTR / CFB / OFB / ChaCha20）外，常见轻量字节码护甲（PRGA / 自修改置换表）。验证时须在同一会话或同一初始状态下做 `decode(encode(x)) == x` 往返闭环，并先核对初始化下发的动态字段是否真正进入变换函数，避免把未参与运算的配置项误判为动态密钥。
7. **定长码点流经变长编码产生的浮动长度**：若 Base64 解码后的字节流长度每次小幅波动，但经 UTF-8 解码成 Unicode 码点序列后**码点总数恒定**，说明内层是定长槽位码点流，外层长度浮动仅因个别槽位值跨过 `0x80`（或 `0x800`）单/多字节边界所致。此类令牌应先解码回码点数组再按槽位对齐比较，直接按字节或 Base64 字符偏移对齐会在首个跨界槽之后整体错位。
8. **按构建重编译字节码中的内嵌分组密钥提取**：当网关每次下发的 JSVMP 脚本字节哈希与字节码偏移均随机重排，且对称分组密码（64/128-bit 块密码）密钥拆散在当次字节码内（既不在接口响应体明文返回，也不以源码数组字面量存在）时，基于固定字节偏移的静态提取会在下次拉取立即失效。对不预展开轮密钥或在每轮反复读取轮密钥窗口的分组密码（如 Feistel / ARX 结构），可在受控本地沙箱执行当次脚本的加密路径，对虚拟机整数寄存器阵列中的连续定长无符号 32 位窗口（如连续 4 个 `uint32` 槽）统计读取频次并降序取候选窗口，再用**同次产出的密文做离线结构自证解密**——筛出解出明文同时满足合法 UTF-8 边界、可打印 ASCII 占比与外层 JSON/分隔符结构不变量的当次密钥（若字节码对密钥字叠加了当次运行期掩码或盐值，可按高频读取常数做小规模组合自证），无需在线试错即可建立跨构建 `decode(encode(x)) == x` 往返闭环。
9. **Latin-1 字节串经 UTF-8 二次编码的 Base64 膨胀特征**：若确认内层为等长流密码异或（UTF-8 明文字节长度 `L`），但外层标准 Base64 解码后的字节长度稳定落在约 `1.5 * L` 左右，且大于 `0x7F` 的字节全部成对呈现 `0xC2 0x80`–`0xC3 0xBF` 合法双字节 UTF-8 形态，说明脚本先把原始密文字节按 `latin1` 映射成单字节码点字符串（`0x00..0xFF`），再按默认 `utf-8` 编码送入 Base64。逆向还原时先将 Base64 解码结果按 UTF-8 解回字符串、取每字符低 8 位（`latin1`）恢复等长密文字节，再与密钥流异或。
10. **参数摘要、请求信封与响应密文的密钥域分离**：同一接口常并存三套互不共享密钥的变换——查询参数哈希签名、绑定会话凭据与 UA 内核族的请求体流式信封（`KS = F(session, UA)`）、以及静态掩码表加压缩（如 `zlib`）的响应体编码。切勿拿请求侧标定出的密钥流直接去扫描响应体或跨接口密文，应先按出入口位置拆成独立往返单元分别标定。
11. **无填充 3 字节探针黑盒恢复 64 项自定义 Base64 字母表**：当外层信封带固定版本前缀且长度按 4 字符分组对齐、疑似换表 Base64 时，不必静态硬抠混淆常量数组——在受控沙箱或页面上下文定位到剥离外层固定前缀后的底层编码函数（确认入参为字节数组/`Uint8Array` 或 Latin-1 单字节串），依次喂入 64 组无填充 3 字节探针 `[i << 2, 0, 0]`（`i = 0..63`，`3 % 3 == 0` 避免触发尾填充，在标准 RFC 4648 高位优先 6-bit 切片 `idx0 = b0 >> 2` 下首索引精确遍历 `0..63`），读取每组输出的首字符并断言去重后恰好为 64 个不同字符（若不足 64 项，排查外层固定前缀未剥离、入参类型不符或低位优先 `b0 & 0x3f` 切位），最后补测一组 `[0]` / `[0, 0]` 确认非 3 倍数尾部采用 `=`、自定义第 65 填充符还是无填充截断。若解码后直接呈现合法 UTF-8 JSON 明文，即可排除外层对称加密假设，把分析收敛到内层子令牌字段。
12. **双代内层前缀判读（程序代次 vs 环境风险评级）与二进制 VM 容器拆解**：当内层子令牌出现两种固定版本前缀且解码字节数稳定落在两档（如一档外层带 Base64 `=` 填充且解码非 16 字节整块对齐 `92 % 3 == 2, 92 % 16 == 12`，另一档无填充且 16 字节整块对齐 `144 % 16 == 0`）时，切勿凭直觉把前缀差异当成“环境降级或风控评分”——应在固定输入下主动置空或篡改画布、音频、样式等高熵探针复测前缀是否翻转；若前缀完全随所加载的动态模块走而不随环境变化，则属于并存的**双代字节码程序**（须用干净会话分别实测服务端是否同时接受两代，避免把单次脏输入报错当成旧代被拒）。对自定义 JSVMP 二进制容器，优先按解释器实际读取顺序拆解头部魔数、隐写掩码位（如从头部特定字节低 2 位提取单字节/多字节 XOR 键）、按解释器字节序编码的代码段长度（`u32BE` / `u32LE` 或变长整数）与变长前缀码常量池，以反汇编指令边界落位和常量池重合度区分“同一解释器下的不同业务程序”与“不同代指令集”。

服务端能恢复的结构，本地用同样的方法也能恢复，这是外层可分析的原因。

## 内层：版式

- 多条样本按头部对齐和按尾部对齐各看一次，可变字段在前时，尾部对齐才能看到稳定骨架。
- 找稳定字节岛、4 字节对齐的小整数、随长度同步增减的偏移。
- 零字节占比和熵值可以区分“明文结构”和“已被掩码”。
- 带长度前缀的可变字段会让后面的结构整体平移，平移后对齐才能比较。

## 判读

- 长度变化本身不是改版信号。可变字段会让长度在一个范围内波动，这个范围也不是协议常量。
- 看结构（魔数、表项数、偏移排布）是否还对得上基线。
- 版本标记变了但信封不变，说明外层算法未换，内层要重新采。
- 结构相同不能证明值可用，服务端是否接受只能在线判断。

## 什么时候停

- 已知结构足够写 S1 校验和换版检测，就停。
- 掩码每次变化、内层字段看不到，继续深挖的成本很高时，先转向运行原始 SDK，把逆向留到业务真正需要的时候。
- 结论写清楚哪部分已还原、哪部分未还原，不把“外层可解”写成“算法已还原”。

## 失效条件

结构结论只对记录的 SDK 版本和日期成立，新版本可能把表和目录一起盖住。文档里写明失效条件，下次改版时逐条核对。
