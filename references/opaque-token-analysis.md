# 不透明令牌分析：信封、版式与批次对比

适用于值带随机掩码、无法逐字比较，或想知道一个长令牌的结构时。这里的目标是获得足够做决策的结构信息，不是把内层字段全部解开。

## 什么时候做

- 要判断“这个值变了没有”“换版了没有”“长度异常是否正常”。
- 要写 S1 校验（本地值结构是否合法）。
- 要决定是否值得继续深挖。

已经能用运行原始 SDK 的方式到 S3 时，内层字段解码可以暂缓。

## 先设计样本批次

一批样本要有受控的差异，否则对比没有意义：

| 变化维度 | 回答的问题 |
|---|---|
| 同一环境，连续多次 | 哪些字节每次都变 |
| 同一环境，重启或隔天 | 是否有时间相关的轮换 |
| 不同账号或环境 | 是否与设备、账号相关 |
| 不同接口 | 是否与 URL 或请求内容相关 |
| 不同 SDK 版本 | 结构是否改版 |

样本落盘时脱敏，记录时间、环境、接口和批次目录，与其他批次对比时写明基线。

## 外层：编码与校验

```bash
python scripts/opaque-token-inspect.py samples.txt
python scripts/opaque-token-inspect.py samples.txt --encoding base64
python scripts/opaque-token-inspect.py samples.txt --encoding custom --alphabet '<64 字符表>' --xor-align
```

1. 看字符集和长度：是否 4 的倍数、有无 `=`，判断 hex、标准 base64、url-safe 或自定义字符表。
2. 自定义字符表可从 SDK 源码常量找到。解码后多条样本应呈现稳定位置。
3. 单字节异或这类按请求变化的掩码，`--xor-align` 会逐条寻找使样本与基准最一致的 key。已知 magic 时可穷举 key 对上它；未知时可用校验位自验证：对每个候选 key 复算校验，能通过的就是当次 key。
4. 找到稳定头部后，判断魔数、长度字段（值等于 Payload 长度）、校验位（复算一致）。

服务端能恢复的结构，本地用同样的方法也能恢复，这是外层可分析的原因。

## 内层：版式

- 多条样本按头部对齐和按尾部对齐各看一次，可变字段在前时，尾部对齐才能看到稳定骨架。
- 找稳定字节岛、4 字节对齐的小整数、随长度同步增减的偏移。
- 零字节占比和熵值可以区分“明文结构”和“已被掩码”。
- 带长度前缀的可变字段会让后面的结构整体平移，平移后对齐才能比较。

## 判读

- 长度变化本身不是改版信号。可变字段会让长度在一个范围内波动，这个范围也不是协议常量。
- 看结构（魔数、表项数、偏移排布）是否还对得上基线。
- 版本标记变了但信封不变，说明外层算法未换，内层要重新采。
- 结构相同不能证明值可用，服务端是否接受只能在线判断。

## 什么时候停

- 已知结构足够写 S1 校验和换版检测，就停。
- 掩码每次变化、内层字段看不到，继续深挖的成本很高时，先转向运行原始 SDK，把逆向留到业务真正需要的时候。
- 结论写清楚哪部分已还原、哪部分未还原，不把“外层可解”写成“算法已还原”。

## 失效条件

结构结论只对记录的 SDK 版本和日期成立，新版本可能把表和目录一起盖住。文档里写明失效条件，下次改版时逐条核对。
