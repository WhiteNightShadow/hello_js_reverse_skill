# 签名来源隔离：未使用的值、绑定关系与新鲜度

把“出值、会话、传输”拆开分别验证。拆开之后，一次失败才能指向一个方向。本文的方法不依赖具体 SDK，但每种做法在目标上是否成立，都要用下面的判据实测。

## 三种来源

| 来源 | 说明 | 用途 |
|---|---|---|
| 页面实发 | 已发给服务端的请求里的值 | 可能一次性，只作结构样本 |
| 页面生成未发 | 页面 SDK 生成，但请求没有离开浏览器 | 控制组、上限证明、R5 路线 |
| 本地生成 | 算法或运行时生成 | 候选 |

每个值都记录来源、是否实际出站、是否被再次签名。比较时写清比的是谁：“与本地成功基线一致”和“与浏览器一致”是两个结论。

## 取得未使用的值

按干扰从小到大选择：

1. **直接调用入口**。在页面主世界调用已定位的出值入口，传完整 URL 和 Body。这样不涉及请求，但入口可能与真实路径不同，要用接受结果或中间值确认。
2. **在发送前截断**。在 SDK 写完头之后、原生发送之前收集结果，不调用原生发送。
3. **让原生层拒绝发送**。让请求停在未发送状态，SDK 仍走完写头流程。
4. **网络层中止**。在浏览器网络层拦截。这时 SDK 认为已发送，内部状态可能已更新，干扰最大。

判据要组合看，只看“发送没抛错”不够：

- 目标请求在网络记录中为 0 条。
- 请求对象状态符合预期，且没有重新 open 或重放。
- 捕获到的头集合完整。Cookie 和部分网络层头由原生存储补齐，要说明哪些不是 SDK 写入的。
- 清理完成，Hook 和捕获都已撤销。

不同浏览器对“先 abort 再 send”这类做法的行为不同，所以要实测判据，不要照搬别处的步骤。SDK 在发送前有异步步骤时，先确认所有头都已写入再收集。

## 避免再次签名

把未使用的值放回页面通道发送时，SDK 的 Hook 可能重新签一次，这时验证的就不是这个值了。用干净的 realm（例如新建 iframe 里的原生 fetch）发送，并核对网络记录里实际发出的值。

## 新鲜度实验

| 问题 | 实验 | 注意 |
|---|---|---|
| 值能否重用 | 同一值发送两次 | 第二次可能计入风控，放到最后做一次 |
| 有效期多久 | 控制生成到发送的间隔 | 先确认会话余量足够 |
| 其余字段能否冻结 | 冻结模板，多次配新真实值 | 这回答模板问题，不回答值的问题 |

历史上“旧值可重放”的结论不能外推到新日期。服务端可以在 SDK 不变时开始校验新鲜度。

## 绑定实验

想知道一个值绑定了什么，用跨来源配对：

| 配对 | 回答的问题 |
|---|---|
| 干净环境产的值 + 目标会话 | 是否绑定登录态或设备 |
| 另一账号产的值 + 目标会话 | 是否绑定账号 |
| 接口 X 的值用于接口 Y | 是否绑定接口 |
| 同一值换 Query 或 Body | 是否绑定请求内容 |

配对成功说明“此刻、此接口不绑定”，不是永久规则。这类实验能大幅缩小范围：如果值不绑定登录，取值环境就可以和业务会话分开。

## 请求头集合的判读

- 多发一个头也可能被拒。一端需要的头，另一端不一定接受。
- 只替换声称的头，其余头及顺序保持模板原样，然后用 [回读](controlled-experiments.md#单变量要回读) 确认。
- 本地同时生成了别的值时，确认它们没有混入请求，也没有被模板值覆盖。

## 观察环境与产值环境分开

包装 Canvas、WebGL、Audio 等原生方法，或反复触发初始化，可能让环境产出的值被拒，而且这种影响可能写入持久化存储，重启后还在。

- 产值环境保持干净，不插桩。
- 观察用一次性环境，用完丢弃。
- 产值环境被污染的迹象：值的长度或结构突变、原本成功的路径开始失败。换全新环境确认，不要继续在被污染的环境里调试。

## 长期运行页面出值

选 R5 作为交付路线时：

- **选对层**：挂在一次产出所有联动字段的函数上，用最少的参数控制最多的变量。不要把签名、随机串、时间戳拆开取再外部重组。
- **活性分级**：端口监听、客户端注册、调用成功、值被服务端接受是四件事，分别确认。
- **失效规则**：断线、导航、文档身份变化后，旧引用和旧结果全部失效，不重放非幂等动作。
- **安全**：能执行任意 JS 的 RPC 只绑本机。

## 什么时候够了

未使用的值加本地 HTTP 到 S3 后，已经证明了上限，出值、传输、会话三段都成立。这时根据业务决定：接受 R5，或者继续往 R4、R1 下探。下探的每一步都用这组基线做控制组。
